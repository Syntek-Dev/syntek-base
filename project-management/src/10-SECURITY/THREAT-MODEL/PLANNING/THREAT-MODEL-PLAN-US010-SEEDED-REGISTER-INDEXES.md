## 1. Scope

This model covers **the generation seam**, not a feature. US010 adds no endpoint, no model, no
screen and no log line; eleven of its thirteen flags read `N/A`
(`project-management/src/02-STORIES/US010.md:121-135`, as read 21/09/2026). It ships Markdown,
one YAML `_tasks` chain, one bash array, and edits to two CI scripts and one CI workflow.

**The asset is a generated project's own registers.** An index is where a developer, and an agent
acting unprompted, reads what a folder holds. Two things can go wrong with it and they point
opposite ways: this repository's rows can reach a project and be read there as the project's own,
or an update can hand a project its blank stub back over rows it wrote. `copier.yml:988-993` names
both as a one-way door for `MEMORY.md`, `GAPS.md` and `DEFERRED.md`; US010 puts seven more files
behind the same door.

## 3b. The update seam in full — why ST01 holds on update, where it does not, and why ST07 must change the seed

Everything in this section was **read in Copier 9.18.2's source, not executed**. The package is
not part of this repository, so a bare line number below is to that release's `_main.py`; the two
other modules cited are named.
`[3/4]` runs whatever Copier `uvx` resolved, unpinned — which is the reason ST07 exists as a
behavioural probe rather than as this paragraph.

**Why the gate holds on every render of an update.** The operation decorator keeps the outer
value (line 115), so every nested render inside an update sees `update`: the old temporary copy
(line 1423), the real destination (line 1472) and the new temporary copy (line 1496). The gated
chain is skipped in all three, so **on update Copier never writes an index path**. ST01 holds by
construction **on `update`** today, because the whole chain sits under the gate at
`copier.yml:1005`.

**Where the gate does not hold.** `run_recopy` is decorated `copy` (line 1316) and calls
`run_copy` (line 1325), and the operation type has two values only, `copy` and `update`
(`_types.py:40`). So `copier recopy` — "as if it were the 1st time you apply the template to the
destination path", in its own help text (`_cli.py:304-306`) — and `copier copy` into an existing
project both open the gate, and the chain moves every seed over the project's own file. No dirty
check guards it: the only one is in `run_update` (line 1348). This is TM-18. It is pre-existing
for nine files, US010 puts seven more behind it, and **no value of the gate can tell the two
apart**.

**What an ungated line would do.** It would run in the old copy, leaving the old blank seed at the
index path there, and in the real destination, moving the new blank seed over the project's
filled index. Copier then takes the diff from the old copy to the project — the project's own
edits (lines 1530-1535) — and replays it onto the destination with `git apply --reject`
(line 1588), which tolerates offset. Then, in the default inline conflict mode (line 266), it
resets any file with a rejected hunk and three-way-merges it with `git merge-file`
(lines 1589-1634), which Copier's own comment notes "might have resolved conflicts automatically"
(lines 1637-1638). Three outcomes follow, and **none is chosen by the author of the line**:

| The seed between the two versions       | Replay result                                    | What the project sees                                                       |
| --------------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------- |
| Byte-identical                          | The project's diff applies cleanly onto the stub | Nothing — the overwrite is invisible                                        |
| Changed, outside the project's hunks    | The diff applies cleanly, at an offset           | The project's rows plus the seed's change — the register altered, no marker |
| Changed, a hunk rejected                | The file is reset and three-way-merged           | The same silent alteration where the edits do not overlap                   |
| Changed, a hunk rejected, edits overlap | The three-way merge leaves markers               | Conflict markers in a register an agent reads unprompted                    |

US010's ST01 says an ungated line "overwrites a project's filled index with a blank stub on every
`copier update`" (`project-management/src/02-STORIES/US010.md:403-404`, as read 21/09/2026). No
row above is that: the overwrite is always followed by the replay. The criterion is right; its
consequence is **corrected** in Section 4b rather than rewritten silently. The round-1 call recorded the changed
case as "rejected hunk / conflict"; the last row is one outcome of three, and the call is **not**
re-opened here — only the wording that carries it is completed (Section 4d, V-3).

**Why this decides how ST07 is written.** The first row is also the case in which a probe passes
whether or not the gate exists. A template that never changes a seed between its two tags cannot
tell a gated task from an ungated one, because the replay restores what the overwrite took. So the
probe has three obligations, and none is optional: the fixture changes **every index seed** between
its tags; the assertion is **byte-identity** with the project's committed edit, never that a marker
row survives, because a silently merged file and a conflict-marked one both contain the marker;
and a self-test mutation that removes the seed task's gate must turn it red. Byte-identity goes red
in all three changed rows, so the probe design stands.

**A pre-existing case of the same shape, raised and not absorbed.** `shipped-ai.py`'s
memory-survival assertion (`:174-175`) runs against a second tag that changes a skill and the
template's own memory (`:207-213`) but never `.copier/MEMORY.md`. By the reading above it would
pass with the memory seed task ungated. That is outside US010's scope and is recorded here so that
ST07's stronger shape is not mistaken for a correction of it. It is routed to `GAPS.md` through
gate 22 (settled 27/09/2026, grilling round 3 Q16; Section 4c item 3).
