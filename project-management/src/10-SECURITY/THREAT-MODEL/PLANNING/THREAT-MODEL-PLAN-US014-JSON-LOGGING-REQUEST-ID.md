## 1. Scope

This model covers **a log pipeline and the claims written about it**, not a feature. US014 adds
no endpoint, no screen, no model and no event; eight of its fourteen flags read `N/A`. It builds
the path every log record already travels — call site, `LogRecord`, filter, formatter, stream,
collector — and corrects the documents that describe it.

**The asset is the log line itself, valued twice and in opposite directions.** As _evidence_ it
must be complete, parseable and correlatable, or an incident cannot be reconstructed (OWASP
`A09:2025`, NIST `DE`). As _disclosure_ it must carry no more than it needs, because every line
reaches whoever can read the collector. The story's settled answers trade the two deliberately:
no redaction ships, `message` is not scrubbed, and the minimisation claim is the staging and
production extras allowlist plus a dropped exception message (grilling 31/10/2026, Q9 and Q11).
This model checks that trade against what Django and the process server actually write.

**The blast radius is a class of projects, not this tree.** This repository's posture is
`development` (`.claude/CLAUDE.md` Section 0) and nothing here is served. The staging and
production `LOGGING` dicts ship into every generated project, so a finding below is a finding about
each of them. That is why the severities read low and why Section 3a exists.

### Surface under review

- **The module** — `code/src/django/apps/core/observability.py`: one `logging.Formatter` subclass,
  wide in dev and minimal in staging and production, and one `logging.Filter` subclass reading
  `apps.core.middleware.current_request_id()`
- **The settings** — `LOGGING` in `dev.py`, `test.py`, `staging.py` and `production.py`, and its
  deletion from `base.py:201-217`
- **The identifier's source** — `RequestIDMiddleware`, second in `MIDDLEWARE`
  (`code/src/django/config/settings/base.py:48-54`), which accepts any inbound `X-Request-ID`
  matching `[A-Za-z0-9._-]{1,200}` (`code/src/django/apps/core/middleware.py:17`, `:40-41`) and
  resets its `ContextVar` in `finally` (`:50-51`). It stores the id only in that `ContextVar` and
  on the response header (`:45-48`), never on the request — so TM-03's constraint needs a change
  here, and that change is in scope of this model: the middleware stores the id on the request
  (gates grilling round 2, 01/11/2026, R2-Q4)
- **Django's own writers** — `django.request` and `django.security.*`, through `log_response`
  (`django/utils/log.py:291-323`)
- **The process server** — Gunicorn with Uvicorn workers, `--access-logfile -` and
  `--error-logfile -` (`code/src/docker/django/entrypoint.prod.sh:21-32`, `entrypoint.staging.sh:30`,
  `entrypoint.test.sh:27`), and staging's `--log-level info` (`entrypoint.staging.sh:29`), which
  becomes `warning`, as production's (`entrypoint.prod.sh:30`; gates grilling round 3, 01/11/2026,
  R3-Q4)
- **The host path** — the new dev bind mount `../logs:/workspace/code/src/logs`
  (`code/src/docker/docker-compose.dev.yml:50-51`)
- **The deploy contract** — `how-to/src/SERVER-ARCHITECTURE/EDGE-REQUIREMENTS.md` entry 13
  (`:276-292`) and the new log-collection section

### Severity scale

| Level      | Definition                                                                |
| ---------- | ------------------------------------------------------------------------- |
| `CRITICAL` | Exploitable without authentication, or full compromise / credential theft |
| `HIGH`     | Exploitable with low-privilege access; significant data or integrity risk |
| `MEDIUM`   | Exploitable under specific conditions; moderate impact                    |
| `LOW`      | Minor impact; defence-in-depth measure                                    |
| `INFO`     | Observation with no immediate exploitability                              |

Only **CRITICAL** and **HIGH** block sprint planning
(`project-management/docs/SECURITY-GUIDE.md`). **This model produced none of either** — read
Section 4 with Section 3a, never alone.

**Most of these rows have no attacker.** Only TM-01, TM-04 and TM-16 have an adversary; the
other seventeen are a claim the code would not honour, a stream outside the pipeline, or a field
that leaks by design. The scale is
attacker-shaped, so a `LOW` here means "no adversary gains much", not "nothing would go wrong".

## 3a. Design-state severity and promotion triggers

**Every severity above is a present-state reading of a template repository that serves nothing.**
Read the table with this one.

| Threat       | Present state | Design state | Promotes when                                                                                                                                |
| ------------ | ------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| TM-01        | LOW           | **MEDIUM**   | Any surface goes live with audit entries joined on `request_id`, or entry 2's CSP nonce activated, and Q7's edge clause not yet deployed     |
| TM-13        | LOW           | **MEDIUM**   | The first production incident where a worker hang or timeout is the cause, or an escaped ASGI exception carries personal data in its message |
| TM-06        | LOW           | **MEDIUM**   | A route ships with a token, an email or another identifier in a path segment                                                                 |
| TM-05, TM-07 | LOW           | **MEDIUM**   | The collector's readers widen beyond the people entitled to the personal data the lines carry                                                |
| TM-14, TM-15 | LOW           | **MEDIUM**   | A deploy repository realises the collector without the label contract the new section states                                                 |
| TM-12        | LOW           | **MEDIUM**   | A project keeps `--access-logfile -` after this story, on a live surface                                                                     |
| TM-20        | LOW           | **MEDIUM**   | A live surface's incident turns on a traceback over 4 KiB written while other workers were logging, or a project raises the cap past 16 KiB  |

**TM-01 and TM-13 are the two to watch.** The first is the only row with an adversary who gains
something — a forged join across the log and audit streams. The second is settled by narrowing the
claim, not by changing the stream (R2-Q1): the process-server lines stay plain text and an escaped
traceback keeps its message, so its promotion trigger is the one most likely to fire.

## 4b. Developer constraints carried forward

Checkable by reading the shipped module, the settings and the two edge clauses. These become US014
acceptance criteria; the assessment numbers them.

1. The filter sets `record.request_id` unconditionally from `current_request_id()`, mapping `""`
   to `None`, and returns `True` — never `setdefault`, never a dropped record (TM-02, TM-18)
2. In wide mode the five fixed keys are written after the extras; in minimal mode only
   `duration_ms`, `status_code` and `method` survive (TM-02, TM-05)
3. A returned 4xx or 5xx `django.request` line carries its response's `X-Request-ID`, proved under
   `Client` and `AsyncClient`. `RequestIDMiddleware` stores the id on the request and the filter
   falls back to the `request` extra's stored id; the stored value is the validated or minted id,
   never the raw header (TM-03; R2-Q4)
4. Minimal-mode `exc_info` is the exception type plus `(filename, lineno, function)` per frame; the
   chain is type-only; PEP 678 notes, `f_locals`, `stack_info` and `exc_text` never appear, and
   minimal mode never delegates to `logging.Formatter.format` or `formatException` (TM-08)
5. The formatter never raises; a serialisation failure still writes one JSON object — the fixed
   field set and the extras, unserialisable values `str()`-coerced in place and the allowlist
   still applied — proved by `json.loads` on the line for a tuple key and a self-referencing dict.
   On a `getMessage()` failure `message` is `str(record.msg)` with no arguments; every coercion
   goes through a guarded `repr` that cannot raise (TM-09; R2-Q5, R3-Q2)
6. Every handler in every environment carries the filter; staging and production console handlers
   declare `ext://sys.stdout`; the mode is asserted per environment (TM-10)
7. Staging, production and test declare the `django` logger with no handlers at `WARNING`, and
   the settings test asserts all three (TM-11; R2-Q2)
8. `--access-logfile -` is gone from the staging, production and test entrypoints (TM-12), and
   staging's process-server `--log-level` is `warning`, as production's (TM-13; R3-Q4)
9. `DJANGO-LOGGING.md` states, in its staging/prod section: `message` is not scrubbed; paths are
   logged, so no secret or PII in a path segment; Django's `BadRequest` and `SuspiciousOperation`
   messages carry `str(exc)` (TM-05, TM-06, TM-07)
10. `EDGE-REQUIREMENTS.md` entry 13 requires the edge to set `X-Request-ID` unconditionally,
    discarding a client value (TM-01)
11. The new log-collection section states the service and environment label contract, `json-file`
    rotation and the retention line (TM-14, TM-15, TM-16)
12. Every "every line", "every entry carries `request_id`" and "no exception message off dev"
    claim is scoped to the lines Django's `LOGGING` emits; the process-server stream — plain text,
    stderr, rarely an escaped ASGI traceback with its message — is documented where the pipeline is

13. The minimal formatter's output, newline included, never exceeds 16 KiB; a longer line is
