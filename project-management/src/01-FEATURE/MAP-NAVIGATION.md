# MAP-NAVIGATION — Can this repository describe itself to a cold agent?

**Charted**: 16/08/2026 · **Charted by**: Sam · **Workflow**: `01-feature`
**Status**: **Resolving** — the two census nodes settled 16/08/2026
**Frontier open**: 10 · **Blocking open**: 3 · **Fog of war open**: 5

> **Template-development artefact.** This map charts work on `syntek-base` itself, not on a
> project generated from it. It is **committed here**, so it syncs across devices, and it is
> emptied out by `copier.yml` `_exclude` at generation — so it never reaches a generated
> project. Every claim below is written to stand on its own.

---

## Destination

**Decide whether this repository needs a third map surface** — a `map/` layer of markdown files,
regenerated by script and corrected by a human at the end of each unit of work, mandated at
`workflows/21-implementation-documentation/` — and if it does, settle what it maps, what generates
it, where it lives, whether it ships to generated projects, and what fails when it rots.

**Done looks like** either a **written refusal** naming what already covers the need, or a built
surface with its generator, its gate, and its mandate wired in. Both are acceptable outcomes; an
unresolved "we should probably do this" is not.

**What this is not.** Not an adoption of ICM. The method was assessed on 16/08/2026 and three ideas
were named as worth taking; **none was adopted**, and this epic decides only the first question ICM
would ask, in this repository's terms.

### The premise is already half-built, and that changes the question

The proposal is "a map, regenerated by script, corrected by a human at the end of each piece of
work, mandated at workflow `21`". **Three of those four already exist**, so the epic is not about
adding maintenance:

| Proposed                    | Already shipped                                                                                             |
| --------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Human-corrected at the end  | `21-implementation-documentation` **Step 5** — update touched `CONTEXT.md` trees, "documentation hard gate" |
| Machine-regenerated         | `21-implementation-documentation` **Step 6** — `code-review-graph update`, docs ⇄ graph lockstep            |
| Mandated at workflow `21`   | Both steps are already mandatory, with `CHECKLIST.md` behind them                                           |
| **A `map/` layer of files** | **This is the only genuinely new thing.**                                                                   |

So the question narrows to: **is there a third map surface worth the cost, given two already exist
and are already mandated at the same gate?**

### The census that makes the case, and its one hard number

| Surface                            | Covers                                            | Maintained by                          |
| ---------------------------------- | ------------------------------------------------- | -------------------------------------- |
| **code-review-graph**              | **188 files** · 859 nodes · 4,147 edges           | `code-review-graph update` (Step 6)    |
| **`CONTEXT.md`/`CLAUDE.md` pairs** | **409 files** — 209 + 200, one pair per directory | Hand (Step 5), gated `docs-pairing.sh` |
| **`REFERENCES.md`**                | Curated index of guides and external primaries    | Hand, ungated                          |
| **Root `CONTEXT.md`**              | The directory tree, one screen                    | Hand, ungated                          |
| **`audits/reports/*`**             | Per-audit findings, JSON + Markdown               | Generated per run                      |

**The hard number: this repository tracks 870 `.md` files against 188 source files.** The
machine-derived map indexes the source and **no markdown at all** — its languages are bash,
javascript, python, tsx, typescript and rust. The hand-curated map is 409 of those 870 files and
describes **its own directory**, not the relationships between documents.

**That leaves ~461 markdown files** — the doctrine this template actually ships — **with no
machine-derived index, no edge set, and no change-impact.** They are covered only by five
single-purpose audits (`doc-references`, `docs-pairing`, `doctrine-drift`, `routing-skills`,
`docs-length`), each of which answers one question and none of which draws a map.

**This is the strongest argument for the epic and it is stated here so N-004 can attack it**: the
number proves an absence of coverage, not a demand for a map. A repository can be navigable without
one.

> **Both numbers were re-measured on 16/08/2026 by N-001 and the paragraph is left as written.**
> "Roughly 175" is **188**, which is exactly the graph's own file count — so the graph indexes
> **188 of 188** source files and 0 of 870 markdown files. The 461 is arithmetically right and
> **rhetorically wrong**: it is not one uncovered lump but 64 skills + 90 workflow files + 307
> others, and the first two classes are gated harder than the pairs are. The corrected census is
> in _Resolved decisions_ below, and it weakens this argument rather than strengthening it.

### The contradiction the proposal contains

"Regenerated via Python scripts **and** human edits" collides head-on with an invariant this
project already holds: **a generated index is never hand-edited** — a file map built by script
cannot drift, a hand-curated one always does. Any design that lets both write to the same file
inherits the failure mode of every stale index in this tree. **N-006 is that collision**, and it is
the sharpest node on the map.

### N-001 — what each surface answers, and what it cannot

| Surface                | Covers                                   | Answers                                                   | Cannot answer                                                           |
| ---------------------- | ---------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------- |
| **code-review-graph**  | **188 of 188** source files · 0 markdown | Call, import, inherit and test edges over **code**        | Anything about a document — markdown is not one of its six languages    |
| **`CONTEXT`/`CLAUDE`** | 409 files (209 + 200)                    | What one directory holds, and how to work in it           | Any relation **between** directories; each describes only itself        |
| **`doc-references`**   | 817 files carrying a citation            | Does this citation **resolve**, here and downstream       | Who cites **me** — there is no reverse edge, and the graph is discarded |
| **`docs-pairing`**     | Every directory                          | Is the pair present, and is each file the right kind      | Whether the content is true, or reachable from anywhere                 |
| **`doctrine-drift`**   | Fenced-code claims table                 | Is this rule stated in a **second** place                 | Anchorless prose — measured and recorded on `MAP-BASE-HEALTH` N-016     |
| **`routing-skills`**   | 243 files carrying `skills:`             | Does the named skill **exist**                            | Whether a guide is reachable **from** any skill (the reverse direction) |
| **`docs-length`**      | Every instructional file                 | Is it under 300 lines, and is it growing in the warn band | Nothing about content, meaning or relationships                         |

**What none of them answers, stated as the four questions a cold agent actually asks:** _which
documents cite this one_ · _what else moves if I change this rule_ · _is this document reachable at
all_ · _which directory owns this concept_. **Not one of the seven surfaces answers any of the
four**, and three of the four are reverse-edge questions over an edge set that already exists.

### The finding that reframes the epic

**The edge set a `map/` layer would draw already exists in the prose, and one audit already parses
it once per run and throws it away.**

- **817 of 870 tracked markdown files (93.9%) carry at least one path-shaped `.md` citation** —
  8,516 backticked path citations and 1,138 markdown links, naming **1,036 distinct** targets.
  That is denser coverage than any frontmatter key and denser than the graph's own 188 files.
- **`doc-references.sh` walks every one of them and retains none.** Its `record()` is called only
  on a failure — `reports/doc-references.md` currently reads `Violations: 0`, which is the whole
  report. The ~9,650 citations that **resolve** are parsed, checked, and discarded.
- **So the raw material for a document graph is already extracted on every audit run.** The
  question N-004 inherits is therefore **not** "can we build an edge set" — it is "should the
  edge set already being computed be **kept**", which is a much cheaper question and points at
  `doc-references.sh` gaining an output mode rather than at a new `map/` surface.

### N-002 — what a generator could key on today

**312 of 870 files (35.9%) carry YAML frontmatter.** It is not spread thinly — it is **total on
three classes and absent from everything else**:

| Class               | Carries frontmatter | Keys available                             |
| ------------------- | ------------------- | ------------------------------------------ |
| `SKILL.md`          | **64 / 64** (100%)  | `name`, `description`, `model`, `metadata` |
| `STEPS`/`CHECKLIST` | **90 / 90** (100%)  | `workflow`, `phase`, `skills`, `model`     |
| Docs guides         | **153 / 162** (94%) | `type: guide`, `skills`, `model`           |
| **`CONTEXT.md`**    | **0 / 209**         | none                                       |
| **`CLAUDE.md`**     | **0 / 200**         | none                                       |
| `src/` artefacts    | 1 / 97              | none in practice                           |

Key totals across the 312: `model` 283 · `skills` 243 · `type` 153 · `workflow` 90 · `phase` 90 ·
`name`/`description` 68 (the 64 skills plus the four generated graph cards).

- **The nine docs guides without frontmatter are not a defect.** They are the two Cloudinary SDK
  dumps and the seven `ai-dictionary/` glossary sub-documents — reference material, not routed
  guides. Recorded so a later session does not chart them as drift.
- **`skills:` is the only real edge in the frontmatter**, on 243 files. Everything else is an
  attribute of the file, not a link to another one. A generator keying purely on frontmatter would
  therefore produce a document → skill bipartite graph and nothing more.
- **The 409 pairs — the largest class, and the one that describes structure — carry no key at all.**
  What they do carry is an `@` import, and it is **100% predictable**: all 200 `CLAUDE.md` files
  import `@./CONTEXT.md`, and 205 import lines resolve to just 4 distinct targets. A generator
  keying on it learns exactly what `ls` already tells it.
- **Consequence for N-004 and N-008:** a frontmatter-keyed generator covers 36% of the estate and
  misses the structural half entirely, while a **citation-keyed** one covers 94% today with no
  authoring change at all. Those are the two designs, and the census says they are not close.

### What each node has to settle

- **N-003 is the highest-leverage node on the map, and it is now the only thing blocking the
  gate.** If the graph can be pointed at markdown, the third surface may be unnecessary and the
  epic closes as a configuration change. Settle it before designing anything. **N-001 sharpened
  what a "yes" has to mean**: the graph indexes 188 of 188 source files, so its coverage of what it
  claims is total — the question is purely whether markdown can join, not whether it would be
  indexed well.
- **N-004 is the gate, and the census has already moved it.** Apply the deletion test: name a
  question a cold agent cannot answer today from the entry file plus two reads. N-001 found four
  that survive — _who cites this_ · _what moves if I change this rule_ · _is this reachable_ ·
  _which directory owns this concept_ — so the deletion test is **not** answered by refusal on
  coverage grounds alone. But it also found that three of the four are reverse-edge questions over
  an edge set `doc-references.sh` already computes and discards, so **the cheapest answer that
  satisfies all four may be an output mode on an existing audit rather than a `map/` layer.** The
  gate must weigh that option explicitly; it did not exist when the map was charted. The guardrail
  still stands — a structure built for something done twice is scaffolding, not architecture.
- **N-005** must not be answered by analogy. ICM's System-map form assumes nouns are code types
  with a `path:line`. Here the durable nouns are **rules, their one enforcement point, and the
  guide that owns them** — which is closer to what `doctrine-drift.sh` already models than to any
  object card.
- **N-006** decides which parts are machine-owned, which are hand-owned, and how they cannot
  overwrite one another. Split files with one owner each is the obvious candidate; a single file
  with both writers is the thing to refuse.
- **N-007** carries four constraints found at charting: the repository root is **exempt from the
  pairing rule**; `/CLAUDE.md` is **already gitignored and generated** by `code-review-graph
install`; any new directory otherwise needs a `CONTEXT.md` + `CLAUDE.md`; and a generated project
  starts near-empty, so a `map/` shipped at generation is empty scaffolding.
- **N-008**: every audit here is bash, `.claude/plugins/*.py` are **read-only by rule and never run
  dev operations**, and the standing non-negotiable is that all dev operations run through
  `code/src/scripts/**/*.sh`. A Python generator would be the first exception and needs to earn it.
- **N-009** inherits a standing lesson from `MAP-BASE-HEALTH`: **a checklist item nobody runs is
  false green.** If the map can rot silently, it will.
- **N-012 is not a feasibility question — the precedent already exists.** The `syntax` skill fronts
  `code/src/scripts/syntax/{check,format,lint}.sh`, and twelve skills invoke scripts today, so
  "a skill can call the generator" is settled before the node opens. Three things are not:

  1. **What a skill adds that the workflow step does not.** A skill fires on **description match**,
     which is probabilistic; a gate must fire **every time**. Step 6 invokes `code-review-graph
update` as a numbered step, not through a skill, and that is the shape a mandate takes here.
     The likely answer is **both, with different jobs** — the workflow step is the mandate, the
     skill is the entry point for regenerating outside a story. The node must state which is
     authoritative when they disagree.
  2. **Whether it runs the verification too, or only the generator.** A skill that regenerates and
     then walks the result cold is worth a 65th skill; one that shells out to a script a human
     could type is a description-matched alias for a filename.
  3. **Whether a 65th skill earns its place at all.** There are **64**, the roster
     (`.claude/skills/CONTEXT.md`) is the only when-to-load table, and every skill is gated by
     `skill-conformance.sh` and `routing-skills.sh`. Adding one has a standing cost.

  **One constraint that does not bite, recorded so it is not re-litigated:** `.claude/CLAUDE.md`
  Section 2.3's "a skill never self-edits" does not block this — the skill would write `map/`, not
  its own definition.

## Fog of war

In scope, not yet sharp enough to state as a decision.

- **Whether change-impact is meaningful for prose.** "If you change this rule, what else moves" is
  the strongest idea in the System-map form, but `doctrine-drift.sh` already finds the second copy
  of a rule. The effects index may be that audit's output rather than a new artefact.
- **Whether this absorbs, replaces, or duplicates `REFERENCES.md`.** It is already a curated index
  of every guide, hand-maintained and ungated — the closest existing thing to the proposal.
- **Whether a generated map would have caught anything real.** `MAP-BASE-HEALTH`'s 16/08
  verification found three live problems from outside itself. If a `map/` layer would have caught
  none of them, its value claim is weaker than the 461-file number suggests.
- **How generated map files interact with the doc gates** — `docs-length.sh` counts instructional
  markdown, `docs-pairing.sh` demands a pair per directory. A generated tree may need an exemption,
  and exemptions are how gates stop biting.
- **Whether the unit of work that triggers regeneration is a story at all.** Workflow `21` is
  per-story; much of this repository's own change arrives as doctrine work that no story describes.
