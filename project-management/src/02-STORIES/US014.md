## Client Summary

The project's guides promise that staging and production write structured, searchable logs with an
identifier tying every line of one request together. Neither is true today: the logs are plain
text and carry no identifier, so the documented searches return nothing. This story makes the
promise true, keeps personal data out of the fields that are written, and corrects the guides that
describe it.

---

## User Story

As **a developer in a generated project investigating a staging or production fault**, I want
**every log line to be one valid JSON object carrying a `request_id`, written by a pipeline the
settings actually configure and queried by the label the collector really sets**, so that **the
LogQL queries in the guides return the lines they describe, and I can follow one request across
its log lines without reading personal data I did not need**.

## Acceptance Criteria

In staging and production every log line is one valid JSON object with a fixed field set and a
`request_id`; dev logs wide and to a mounted host path; test stays console-only; every handler in
every environment carries the filter; and the documents that describe the pipeline describe this
one.

```gherkin
Scenario: A staging or production line is one valid JSON object with the fixed field set
Given config.settings.staging or config.settings.production
When anything logs a record, including one whose message holds a quote, a backslash or a newline
Then stdout receives exactly one line — the console handler writes to stdout, not StreamHandler's default stderr — and that line parses as a JSON object
And it carries timestamp (ISO-8601, UTC), level, logger, message and request_id (grilling 31/10/2026, Q4)
And it carries exc_info only when the record has one
And no other key appears unless it is an allowlisted extra

Scenario: request_id is always present
Given a record logged while RequestIDMiddleware is serving a request
Then request_id equals current_request_id() for that request
Given a record logged outside any request — at start-up, or from a management command
Then the request_id key is present and its value is null, never "" and never missing (Q5)
Given a view that returns, rather than raises, a 4xx or 5xx response
When django.request logs that response
Then its line's request_id equals the X-Request-ID header of the same response, not null

Scenario: Staging and production keep only the allowlisted extras
Given a call site passing extra={"duration_ms": 12, "status_code": 200, "method": "GET", "email": "a@example.com"}
When the record is formatted under staging or production
Then duration_ms, status_code and method are serialised
And email is dropped, not masked and not renamed (Q9)
And under dev the same record serialises every extra (Q9), an unserialisable one as its str() — so a django.request record's request object appears as its repr, query string included

Scenario: Staging and production log an exception's type and frames, not its message
Given a record logged with exc_info for ValueError("user a@example.com not found")
When it is formatted under staging or production
Then exc_info carries the exception type and the stack frames
And the exception's message text appears nowhere in the line (Q11)
And under dev exc_info carries the full traceback, message included (Q11)

Scenario: Levels follow the environment
Then the root logger is at WARNING in staging and production, and at DEBUG in dev (Q10)
And dev keeps the django logger at INFO and django.db.backends at WARNING, file only (dev.py, unchanged)
And test keeps one console handler with no formatter, root at WARNING — it carries the filter only so the every-handler invariant holds

Scenario: The filter is on every handler in every environment
Given each of config.settings.dev, test, staging and production
Then every handler in its LOGGING declares the request_id filter
And base.py assigns no LOGGING, and its "replaces this wholesale" comment is gone

Scenario: Dev log files reach the host
Given the dev stack brought up with code/src/scripts/development/server.sh
When the django service writes to its RotatingFileHandler at /workspace/code/src/logs/django.log
Then the same file is readable on the host at code/src/logs/django.log
And code/src/logs/ stays gitignored for *.log and *.log.*
```

### Backend Acceptance Criteria

- [ ] `code/src/django/apps/core/observability.py` exists — the path `DJANGO-LOGGING.md`:35 already

      library only

      environment
