## Client Summary

The project's guides promise that staging and production write structured, searchable logs with an
identifier tying every line of one request together. Neither is true today: the logs are plain
text and carry no identifier, so the documented searches return nothing. This story makes the
promise true, keeps personal data out of the fields that are written, and corrects the guides that
describe it.

---

## User Story

As **a developer in a generated project investigating a staging or production fault**, I want
**every line Django's `LOGGING` emits to be one valid JSON object carrying a `request_id`, written by a pipeline the
settings actually configure and queried by the label the collector really sets**, so that **the
LogQL queries in the guides return the lines they describe, and I can follow one request across
its log lines without reading personal data I did not need**.

## Out of Scope

- **Redaction and scrub keys** — the deferred half, homed in a future `syntek-observability`
  package with its trigger on the map (N-020). Nothing is written to `syntek-modules`.
- **OTLP tracing and metrics** — the same deferred half.
- **Named loggers and application instrumentation** — a generated project adds its own once it
  has features to log (N-020).
- **The security and audit stream** — `MONITORING-AND-INCIDENT.md`:41's field list governs it;
  this story states the split and builds only the application stream.
- **A non-Loki project's query language.** US013 holds four `Loki` sites literal because LogQL is
  Loki's (US013 Out of Scope; its dated note on the S-07 row). This story rewrites the LogQL
  **selectors** under the reference-stack marker US013 places; it does not translate the queries
  for another aggregator.
- **The Prometheus scrape job** `HEALTH-CONTRACT.md`:106 (`<%ORG_SLUG%>-backend`, `service = "web"`)
  — a metrics label, not a Loki selector; the same drift, not this pipeline.
- **The retrieval procedure and the block on Claude reaching a server** — `S-08`, `Held`.
- **Routing Gunicorn's and Uvicorn's error log through Django's `LOGGING`** — rejected (gates
  grilling round 2, 01/11/2026, Q1). The process-server stream stays plain text on stderr, and this
  story documents it with a selector that keeps it. An escaped ASGI exception's traceback keeps its
  message there, which is the accepted residual the threat model's TM-13 promotes on.
- **A per-subject search of the log store** for an access or erasure request: the Art. 11 position
  is recorded in the GDPR plan, flagged for legal sign-off (gates grilling 01/11/2026, Q4). Under
  Art. 11(2), a request in which the subject supplies a `request_id` may have to be served against
  the lines it keys; how a project serves one is its controller's decision, within the legal
  sign-off (gates grilling round 2, 01/11/2026, Q7).
- **Correlating records outside `RequestIDMiddleware`'s dynamic extent** — a streaming or file
  response body generated after the view returns, a thread or executor a view starts (on the
  default, non-free-threaded build, where a new thread starts with an empty context), and an
  exception raised mid-stream under ASGI (which escapes to the process-server stream). Their
  records carry `request_id` null and are recorded as uncorrelated, in `DJANGO-LOGGING.md` and
  here, pinned by a test; carrying the id across them is not built (gates grilling round 3,
  01/11/2026, Q3).
- **Atomicity of a line over 4 KiB (`PIPE_BUF`) across workers.** The minimal line is capped at
  16 KiB, so Docker never splits it, but two workers writing lines over 4 KiB at once can still
  interleave on the shared stdout pipe. That rare case is an accepted residual, not fixed here
  (gates grilling round 3, 01/11/2026, Q1).
