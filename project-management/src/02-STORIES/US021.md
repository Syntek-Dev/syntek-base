## Client Summary

Today the template is test-generated in only two ways, with and without the mobile app, although
it offers seventy-two valid combinations of options. This story generates every one of them on
each change and checks each result in full, so a combination nobody happened to try can no longer
ship a broken or leaking project.

---

## User Story

As the maintainer of syntek-base, I want every valid combination of the template's offered options
generated and checked in full on each change, so that "the template generates a correct project"
is measured for every configuration a developer can choose, rather than inferred from two.

## Dependencies

- **US010** (The seven register indexes are born seeded — lands the three new generated boards,
  their seeds in the copy-gated task, `shipped-boards.sh` at eight boards, and the joined-line
  instruction search in `[3/4]`). This story's seed rows read the eight boards and its instruction
  row reads that search, so it **merges after US010** and rebases onto its `audit-template.yml`
  edits. It does not wait for US010 to start: the case enumeration, the evidence record and the
  render loop are independent of the boards.
- **US012** (A seeded file that never lands is reported — the check-4 `SEEDED` presence loop).
  **Neither blocks the other.** Where US012 has landed, its full check-4 run is one of this
  story's per-case gates; before it lands, an explicit completeness assertion supplies presence
  evidence, as approved on 09/10/2026. US012's "every render path" criteria are ticked from this
  story's runs, and stay recorded as unmeasured until this story lands.
- **MAP-NATIVE-MOBILE-SURFACE** (charting) may delete `INCLUDE_MOBILE`. That changes the case
  count, not this story's shape: the selector-drift criterion below is what makes the change land
  in the same change as the matrix. A risk, not a hold (CUT-PLAN.md P11).
- **The pinned Rust toolchain** and its provisioning in CI, for cases with `INCLUDE_RUST` true.
  Absent provisioning makes those cases unrun, never green.

## Open questions

<!-- No map fog item is carried: this story has no slice row. These are the build questions the
     approved design leaves to the plan, each answered at 17-story-plans with Sam before the story
     leaves Open. -->

- **Execution shape.** The approved design requires 72 complete renders per run, and
  `audit-template.yml` may not contain GitHub expression syntax, which rules out a job `matrix:`.
  One sequential loop, a sharded set of jobs with literal case lists, or a separate workflow file
  outside the rendered tree? This is a cost and runtime question for Sam, answered at the plan.
- **Trigger.** Does the full matrix run on every pull request into the branch chain, or on a
  narrower trigger (pushes to `testing` and up, or a path filter on `copier.yml`, `.copier/` and
  the render script), with the two-case loop kept for the rest? Whatever runs less than every pull
  request must say so in its job name, so a green run is never read as exhaustive.
- **Rust provisioning.** Does the job install the pinned toolchain itself, or use a runner image
  that carries it? Either way the 36 Rust-enabled cases depend on it.
- **Retention.** Is a case's evidence a retained artefact (the tree, or its gate log), and for how
  long? The approved design accepts either a retained tree or an immutable gate log.

## Acceptance Criteria

Every one of the 72 valid configuration cases named in the US010 story plan is generated from the
recorded source SHA and passes every gate applicable to it, each with its own evidence; a missing
case, an unrun gate or a selector the matrix does not enumerate is reported, never absorbed.

```gherkin
Scenario: Every valid case is generated, gated and accounted for
Given the 72 case IDs CFG-01-C0-P0 to CFG-12-C1-P2 approved on 09/10/2026
When the [3/4] Template Generation job runs on a commit
Then each case is rendered from that commit's SHA with the normal copy tasks enabled
And each case records its ID, its effective answers read from its rendered .copier-answers.yml, the source SHA, the run ID and the exit code of each gate
And the run lists 72 distinct case IDs, with no duplicate standing in for a missing case

Scenario: One failing case does not hide the cases after it
Given a commit on which one case fails a gate
When the job runs
Then every remaining case is still rendered and gated
And the job fails, naming the failing case ID and gate

Scenario: A missing or duplicated case is reported
Given a probe that removes one case from the enumeration, and a probe that repeats one
When the enumeration check runs against each
Then each probe fails, naming the case

Scenario: A selector the matrix does not enumerate is caught
Given a copy of copier.yml with one boolean question or one choice added
When the selector-drift check compares the offered selectors with the matrix's own list
Then it fails, naming the selector
And the matrix and its expected count change in the same change as the selector, never later

Scenario: An invalid tuple is never counted as a case
Given INCLUDE_DESKTOP is asked only when INCLUDE_RUST is true
When the enumeration is built
Then no case sets INCLUDE_DESKTOP true with INCLUDE_RUST false
And a skipped desktop answer is not labelled as a separate valid case

Scenario: A missing prerequisite is an unrun case, never a pass
Given a run in which the pinned Rust toolchain is unavailable
When the Rust-enabled cases are reached
Then each is reported as not run, with the prerequisite named
And the job does not report exhaustive coverage

Scenario: A gate is N/A only where its optional group is absent, and the absence is asserted
Given a case with an optional surface disabled
When that surface's path-group gate runs
Then it is N/A only because the group is absent by the case's answers
And the corresponding exclusion assertion passes for that case
And the whole-tree token, leakage, completeness, board and instruction gates still run
```

**The gates on every case.** As approved on 09/10/2026, with the seed and instruction rows
re-based on US010's re-cut (see the provenance note).

| Gate                                  | Required evidence                                                                                                                                                                                                 |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Successful complete render            | Source SHA, case ID, effective answers, run ID, exit code, and a retained tree or immutable gate log                                                                                                              |
| Token substitution                    | No unintended unrendered token anywhere in the tree; only the existing TEMPLATE-GUIDE and TEMPLATE-TOKENS prose exceptions                                                                                        |
| Template and instance leakage         | The template-only exclusions hold, `.copier/` is removed, and the full `shipped-artefacts.sh` run passes on this tree; no template record or task-map ID leaks                                                    |
| Seed presence and completeness        | The baseline completeness list plus the eight board paths; US012's check-4 `SEEDED` run where landed, otherwise the explicit completeness assertion                                                               |
| Board content                         | Each of the eight boards in the tree is byte-identical to its seed, and `pm-board.sh --check` passes in the generated tree, so no board carries a syntek-base row and none is stale on day one                    |
| Instruction closure                   | The joined-line instruction search over the tree's Markdown, by paragraph, printing its pattern and output, failing on any hit, skipping dated historical comments                                                |
| Branding and dependency lock          | The manifest carries the synthetic slug; a present lock agrees and names no template package; a failed or absent lock is incomplete evidence, never a pass                                                        |
| Version and accumulator seeds         | Root version 0.1.0 and one fresh entry in each release log; every present sub-package seed log, mobile included when enabled; `MEMORY.md`, `GAPS.md`, `DEFERRED.md` and `CUT-PLAN.md` blank                       |
| Optional paths and routing            | Every conditional path group in `copier.yml` present when enabled and absent when disabled, skill aliases, guides, scripts and workflows included; enabled files and symlink targets resolve                      |
| Rendered posture and preserved syntax | Both posture carriers equal the case's answer; GitHub expression and shell-test syntax survive in the files that ship for this case, counted for this case                                                        |
| Shared-file consistency               | Across cases with identical branding and posture, common rendered files obey the no-conditional-file-content rule over every selector edge; Git internals and the answers file excluded; locks validated per case |

### QA Acceptance Criteria — Automated

- [ ] Integration: the `[3/4]` job on the landing commit lists 72 distinct case IDs, each with its
      answers, SHA, run ID and per-gate exit codes, read from the run by its recorded ID
- [ ] Integration: the enumeration check is red on the missing-case and duplicate-case probes,
      and green on the real enumeration
- [ ] Integration: the selector-drift check is red on a `copier.yml` copy with one added boolean
      and on one with one added choice, and green on the real file
- [ ] Integration: a planted gate failure in one case leaves every later case gated, and the job
      fails naming that case
- [ ] No pytest, no coverage figure, no migration check — each recorded `N/A` with its reason:
      this story ships no application code

### QA Acceptance Criteria — Manual

- [ ] The landing run's case table is read by hand against the twelve surface rows and the six
      ClickUp-by-posture suffixes, and every N/A cell is traced to an absent optional group
- [ ] An unrun case, if any, is reported as unrun with its prerequisite named, and the run is not
      described anywhere as exhaustive
- [ ] A tester other than the author has signed the walk-through off
