## Client Summary

Setting up the project installs its automatic code-quality checks as a visible, deliberate step,
instead of leaving them to switch themselves on later at an unpredictable moment. The setup guide
already tells people this happens; after this change, it is true.

---

## User Story

As a **developer setting up this project for the first time**, I want **the git pre-commit hooks
installed as an explicit, reported step of `install.sh`**, so that **the quality gates are either
armed and visible from the first commit, or absent and known — never arming themselves silently at
a moment I did not choose**.

## Acceptance Criteria

`install.sh` installs the git hooks as an explicit, reported step, and reports honestly when it
cannot. The `--ignore-scripts` supply-chain control is unchanged on every branch that carries it.
The setup instruction that already promises this behaviour becomes true without being edited.

```gherkin
Scenario: The hooks arm as an explicit step of a first-time install
Given a freshly cloned checkout with no `.git/hooks/pre-commit`
When the developer runs `bash install.sh`
Then a step after "JavaScript dependencies" runs `lefthook install`
And the step prints its own success line in the house `ok` idiom
And `.git/hooks/pre-commit` exists and is lefthook's generated hook
And a subsequent `git commit` runs the `lefthook.yml` pre-commit legs

Scenario: The supply-chain control is untouched
Given the change is applied
When `code/src/scripts/development/install-frontend.sh` is read
Then `--ignore-scripts` is present on all three pnpm invocations
And `package.json`'s `prepare` script is unchanged
And no pnpm lifecycle script is enabled anywhere to arm the hook as a side effect

Scenario: Re-running the install does not break an already-armed checkout
Given `.git/hooks/pre-commit` already exists from a previous run
When the developer runs `bash install.sh` again
Then the step completes successfully
And the hook remains lefthook's and is not duplicated

Scenario: A checkout with no git directory is skipped, not failed
Given a tree exported without `.git`
When the developer runs `bash install.sh`
Then the step reports that hook installation was skipped because there is no git repository
And the install continues
And the overall exit code is unaffected by the skip

Scenario: A genuine hook-install failure stops the install
Given a git checkout where `lefthook install` cannot complete
When the developer runs `bash install.sh`
Then the failure is reported in the house `err` idiom naming `lefthook install`
And the script exits 2, matching the "install failed" code its own header declares
And the failure is not swallowed as a warning

Scenario: The shipped setup instruction becomes true without being edited
Given `.copier/README.md:441` states that `install.sh` "runs `lefthook install`"
When the change is applied
Then that sentence describes what the script does
And the file is not modified by this story
```

### Security Acceptance Criteria

- [ ] [US009/ST01] `--ignore-scripts` remains on `install-frontend.sh:67` (`--check` branch),
      `:84` (`--local` branch) and `:93` (lockfile-only branch) — asserted, not assumed
- [ ] [US009/ST02] `package.json`'s `prepare` script is byte-identical after the change; the hook
      is armed by the explicit step, never by re-enabling a package-manager lifecycle script
- [ ] [US009/ST03] The `lefthook install` step runs the binary resolved from the project's own
      `node_modules`, not a globally-installed one — the version that arms the hook is the pinned
      `lefthook` devDependency (`package.json:22`), so the hook is not whatever the host happens to
      have
- [ ] [US009/ST04] The step runs **after** dependency installation, so it can never arm a hook that
      references a toolchain not yet present — the failure mode N-019 rejects a copier `_task` for
      (`MAP-GATE-PARITY.md:241-244`)
- [ ] [US009/ST05] The step introduces no new network fetch, no new credential read, and no new
      write outside `.git/hooks/`
- [ ] [US009/ST06] The `.git` guard tests for a repository and nothing else; it does not become a
      general try/ignore that would hide a real failure (the `|| true` shape in `package.json:11`
      is correct for a lifecycle script and wrong for an explicit step)
